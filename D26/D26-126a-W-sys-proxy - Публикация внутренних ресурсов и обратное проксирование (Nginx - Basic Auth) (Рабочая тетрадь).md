# `D26-126a-W-sys-proxy`: Публикация внутренних ресурсов и обратное проксирование (Nginx / Basic Auth) (Рабочая тетрадь)

> - 📝 **Описание:** Практикум направлен на **формирование навыков** организации безопасного доступа к внутренним ресурсам (DMZ) через технологии статической трансляции (Port Forwarding), обратного проксирования (Reverse Proxy) и HTTP-аутентификации.

## Вводная

До этого момента мы строили «Вещь в себе» — сервисы, работающие только внутри защищенного периметра. Но бизнес требует, чтобы сайты видели клиенты, а администраторы могли управлять серверами из дома. Мы должны «просверлить» контролируемые отверстия в нашей обороне.

Мы реализуем **Многоэшелонную защиту**.
1.  **Сетевой уровень (L3/L4):** На граничных маршрутизаторах мы настроим **DNAT** (Port Forwarding), чтобы пропустить трафик внутрь на строго определенные порты.
2.  **Прикладной уровень (L7):** На сервере провайдера (`ISP`) мы поставим "умного швейцара" — **Nginx Reverse Proxy**. Он будет анализировать доменные имена (`web...`, `docker...`) и перенаправлять запросы на нужные внутренние IP.
3.  **Аутентификация:** Для корпоративного портала мы включим проверку паролей на уровне Nginx, отсекая чужаков еще на дальних подступах.

> 3. **Внедрить** механизм принудительной базовой аутентификации (Basic Auth) для защиты чувствительных веб-ресурсов.

> 💻 **В терминале маршрутизатора `HQ-RTR`:**
>
> > 📥 **Примените** правила проброса портов (DNAT) и маскарадинга.
> >
> > В правилах для SSH мы применяем технику **Port Redirection**: принимаем соединение на внешнем порту **2026**, но перенаправляем его на стандартный порт **22** внутреннего сервера. Это позволяет выполнить требование без перенастройки SSH-демона на самой целевой машине.
> >
> > > ⌨️ **Впишите** вместо `[Имя WAN-порта]` физическое имя вашей сетевой карты, смотрящей в Интернет (например, `enp7s1` или `ens18`). Сохраните кавычки `""`!
> >
> > ```bash
> > mkdir -p /etc/nftables
> >
> > cat <<EOF > /etc/nftables/nftables.nft
> > #!/usr/sbin/nft -f
> > flush ruleset
> > table ip nat {
> >     chain prerouting {
> >         type nat hook prerouting priority dstnat;
> >         iifname "[Имя WAN-порта]" tcp dport 8080 dnat to 192.168.1.10:80
> >         iifname "[Имя WAN-порта]" tcp dport 2026 dnat to 192.168.1.10:22
> >     }
> >     chain postrouting {
> >         type nat hook postrouting priority srcnat;
> >         oifname "[Имя_WAN_порта]" masquerade
> >     }
> > }
> > EOF
> >
> > systemctl restart nftables
> > nft list ruleset
> > ```
>
> > 📤 **Ожидаемый вывод:**
> > Ищите глазами цепочку `prerouting`. Наличие адреса `192.168.1.10` подтверждает, что ядро Linux успешно загрузило ваши правила публикации (Port Forwarding) в память.
> > ```text
> > table ip nat {
> >         chain prerouting {
> >                 type nat hook prerouting priority dstnat; policy accept;

> >         }
> > ...
> > ```

---

> 🤔 **Мысли**
>
> 🎩 **Шляпник о подмене лиц:**
> NAT — это не маршрутизация, это маскарад (буквально). Пакет приходит на роутер с одним «лицом» (Внешний IP). Роутер стирает его и рисует другое (Внутренний IP).
> 
> Сервер внутри сети даже не догадывается, кто к нему пришел на самом деле. Весь трафик для него исходит от шлюза. Мы обманываем сервер ради его же безопасности.

### 2.1. Публикуем и защищаем веб-ресурсы (3 балла)

>

> Nginx будет принимать запросы на красивые доменные имена и пересылать их на внешние порты (`8080`) наших маршрутизаторов. А те, благодаря настроенному в Разделе 1 DNAT, перешлют их конечным серверам.
> 
> Для сайта `web.au-team.irpo` (Корпоративный портал) мы сразу активируем **Basic Authentication**. Это создаст эшелонированную защиту: даже если хакер знает адрес, он не пройдет без пароля.
